Exercise 7

Simulate more client traffic as in exercise 6. Experiment with HA and its status reports in the Stork UI by stopping kea-dhcp4 and kea-dhcp6 on "kea1".

  1. Connect to "client" a second time via ssh, as you will need to run perfdhcp twice simultaneously. Choose one session to call "dhcp4 client" and one to call "dhcp6 client".

  2. On "dhcp4 client", run a simulation of 100 DHCPv4 clients at a rate of 10 per second with the following command:
    perfdhcp -l eth1 -4 -r 10 -R 100 -Y 1 -y 3600 -t 15
    ⎘ COPY
  1. On "dhcp6 client", run a simulation of 100 DHCPv6 clients at a rate of 10 per second requesting both an IA_NA and an IA_PD with the following command:
    perfdhcp -l eth1 -6 -r 10 -R 100 -e address-and-prefix -Y 1 -y 3600 -t 15
    ⎘ COPY
  1. Simulate an outage of the kea-dhcp4 service on "kea1" by running the following command to stop the service:
    systemctl stop isc-kea-dhcp4-server
    ⎘ COPY

  1. Verify that the perfdhcp instance running in your "dhcp4 client" window starts to report drops.

  2. Check the status to see if the failover has occurred. The -Y 1 -y 3600 parameters passed to perfdhcp tell the tool to simulate an outage by reporting that an increasing number of seconds have elapsed while it has been trying to get an address as a real client would. Kea watches for this when performing failover calculations. To check the current status, execute this command on "kea2":
    echo '{ "command": "status-get" }' | socat unix:/run/kea/socket4 - | jq
    ⎘ COPY

    In the output from the command, look for "server-name": "server2", with "state": "partner-down", and "last-state": "unavailable", with "server-name": "server1", in the "remote": { } section. It may take a couple of minutes for this to occur; there are parameters that can be set in the Kea configuration to control how quickly this happens. Once the value of "state" is "partner-down", move on to step 7.

  1. Look again at the "Dashboard" under the "DHCP" menu in the Stork UI. There should be a warning triangle and "partner-down" in the "HA State" for "kea2". "kea1" should have a red X in status and "unavailable" in the HA State.

  2. Verify that drops have stopped incrementing on "dhcp4 client".

  3. Shut down kea-dhcp6 on "kea1" by executing the command:
    systemctl stop isc-kea-dhcp6-server
    ⎘ COPY

  1. Verify that drops have started incrementing in perfdhcp running on "dhcp6 client".

  2. As in step 6 for kea-dhcp4, check the current status of kea-dhcp6 on "kea2" by running:
    echo '{ "command": "status-get" }' | socat unix:/run/kea/socket6 - | jq
    ⎘ COPY

    You are looking for the partner-down states in the output as described in step 6. Once the state matches that described here, move on to step 12.

  1. Verify in the Stork UI that the states for kea-dhcp6 on "kea1" and "kea2" are similar to those described in step 7.

  2. Notice in the "Events" log on the Stork UI that the times for the onset of trouble are shown.

  3. Verify that drops have stopped incrementing in perfdhcp running on "dhcp6 client".

  4. Conclude the outage by restarting kea-dhcp4 and kea-dhcp6 on "kea1" with the following commands:
    systemctl start isc-kea-dhcp4-server && systemctl start isc-kea-dhcp6-server
    ⎘ COPY

  1. Use the API commands described in steps 6 and 11 to check the status of HA. Watch the "Events" log in the Stork UI for events relating to the return to service. Finally, click the refresh button next to "DHCP Dashboard" in the Stork UI after a couple of minutes, and see that everything is working again.

  2. Stop perfdhcp on "dhcp4 client" and "dhcp6 client" by pressing ctrl+c in their respective ssh windows.
